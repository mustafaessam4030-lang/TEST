# ATLAS Logistics Knowledge Engine

What ATLAS knows about logistics and supply chain management is written down
as versioned knowledge items. ATLAS searches them, explains them, connects
them to this platform's rules and your data, and cites where they come from.
The items are reviewed and changed through a controlled process. No answer
in this engine is generated by a language model.

| | |
|---|---|
| Curriculum and taxonomy | `knowledge/curriculum.json` |
| Sources (checked, with dates) | `knowledge/sources.json` |
| Knowledge items, in git | `knowledge/items/A_fundamentals.json` … `F_problem_solving.json`, `P_atlas_project.json` |
| Engine: load, validate, search, graph | `intelligence/kb.py` |
| Answers (layers, citations, status) | `intelligence/kb_answer.py` |
| Exact calculations, Incoterms table | `intelligence/kb_calc.py` |
| Governance: propose, review, ingest, audit | `intelligence/kb_govern.py` |
| Lessons from runs | `intelligence/kb_lessons.py` |
| Assessment set and runner | `knowledge/eval/eval_v1.json`, `tools/kb_eval.py`, `knowledge/eval/REPORT.md` |
| Tests | `test_knowledge.py` (plus the ATLAS suites) |

## 1. What already existed, and what was reused

The audit, before any code was written, found the following:

- **A short glossary.** `intelligence/knowledge.py` held about 25 hand-written
  definitions (20 general, 8 for the automation's own terms). They had no
  sources, no Arabic and no review status. The general ones are now items in
  `knowledge/items/`, with their wording kept so existing answers did not
  change. `knowledge.glossary()` reads from the engine. The automation's own
  terms (Needs review, Partial, Skipped…) stay where the assistant uses them;
  they are also items in domain P, and a test keeps the two identical.
- **Keyword search over the guides.** `handbook.py` already searched the
  project guides with BM25. The engine uses the same scoring, adds synonym,
  acronym and Arabic-spelling expansion, and gives a strong boost when a
  question names an item outright.
- **The ATLAS store** (`intelligence/store.py`). Governance keeps its
  append-only log in the same folder. It uses the store's redaction and its
  rule that test data can never mix with production data.
- **The verified learning store** (`intelligence/learning.py`). Lessons are
  derived from it rather than kept a second time.
- **Roles and permissions** (`controlplane/rbac.py`). Two permissions were
  added: `knowledge.propose` (Operator, Admin) and `knowledge.review` (Admin).
- **No embedding model and no vector database** exist anywhere in the
  platform. None was added. Retrieval is ranked keyword search, and that
  limitation is stated in every report.

## 3. The item schema

```
id               "C.incoterm-fob"   domain letter + slug, never reused
kind             concept | term | kpi | process | document | rule | case | party | incoterm | lesson
term, acronym, full_form, synonyms[], terms_ar[]
definition, definition_ar, explanation
definitions[]    {context, text} when the meaning genuinely depends on context
example, scenario, misconceptions[], limitations[], preconditions, exceptions
domain, category, difficulty (1 foundation, 2 intermediate, 3 advanced)
related[]        {id, type}  is_a, part_of, contrasts_with, causes, measured_by,
                 documented_by, precedes, applies_to, example_of, related
sources[]        {source (an id in sources.json), section, page, note}
evidence_status  project_verified | source_cited | general_knowledge | unverified
scope            general | project (this platform's code) | business (a Mantrac
                 SOP) | jurisdiction (a country's rule)
jurisdiction, edition, effective_from, review_by
kpi              {formula, unit, aggregation, period, fields[], exclusions[],
                 limitations[], convention: industry | business | atlas}
review_status    unreviewed | reviewed | approved | superseded | retired
version, created, updated, superseded_by, reviewed_by, reviewed_at, origin
```

`kb.validate()` enforces the following, and a test fails if any item breaks them:

- Required fields are present.
- Cited sources exist in the registry.
- Related ids exist.
- `project_verified` cites a file in this repository.
- `source_cited` cites an outside source.
- A project rule is project-verified.
- A business rule cites an approved internal document.
- A country rule names its country, cites the national authority and has a review date.
- A KPI has every field of its measurement block.

**Honesty rules for content**:

- No page number is given unless it was checked; none in the repository is.
- No URL is listed that was not checked. `sources.json` records the date and
  the HTTP status of each check. ISO answered 403 to the check, so it is
  marked as not confirmed reachable.
- A definition carried over from the old glossary is `general_knowledge`. It
  is not "verified", because coming from a project file does not prove it.
- The two country rules are marked `unverified` until a reviewer checks them
  against the authority:
  - Ghana: duty is charged on the CIF value.
  - Egypt: shipments need advance cargo information (ACI).
- All 165 repository items start `unreviewed`. Answers say "not yet reviewed
  by a Mantrac expert" until a reviewer approves them.

## 4. How ATLAS answers

A question reaches the engine when ATLAS's run rules did not answer it. It
also reaches the engine when only the engine can answer it: an Incoterms
"who does what", a calculation with its numbers, a comparison of two known
concepts, or "what does X mean".

A question about your data never gets a definition instead of the data. That
covers:

- a shipment reference;
- "my/our/this shipment";
- "how many", "which", "show";
- "what is the ETA?";
- this run.

Those questions are answered from the records.

An answer is built in labelled layers:

1. **The answer.** It comes from one of these:
   - a definition, plus its explanation, example, misconceptions and any
     context-dependent meanings;
   - the Incoterms table;
   - a comparison;
   - an exact calculation.
   An Arabic question gets the Arabic definition first.
2. **In this platform / Mantrac's rule.** Where the platform or a Mantrac SOP
   applies its own rule. A general definition never overrides it, and the
   answer says which one decides.
3. **In your data.** Only for items that are this platform's own figures:
   - the past-due share and the eHub on-time flag, only for a role that may
     open Clearance;
   - Needs review, Skipped and Partial in this run.
   For "what is *our* OTIF", the answer says this platform does not hold the
   data the KPI needs and that it won't estimate the figure.
4. **Country-specific warnings.** These give the country and the authority,
   whether the item is unverified, and whether its review date has passed.
5. **Related concepts** from the concept graph, with the relation.
6. **Sources.** Each one has its publisher, URL or file and section, and
   whether the page was checked. A general definition without a checked
   source says so.
7. **Knowledge status.** The item id, version, evidence status, review status
   and edition.

Knowledge answers are not reworded by a language model, because the
citations and status lines must reach the reader exactly as written.

**Calculations** (`kb_calc.py`) cover OTD, OTIF, exception rate, past-due
share, cost per shipment, cost variance, chargeable weight (with the
carrier's divisor), chargeable days after free time, transit days, and
demurrage vs detention by location. They follow these rules:

- **Inputs are read by meaning.** "X of Y", the words next to each number,
  or the order they were written.
- **Never reordered.** Numbers are never reordered by size, and an impossible
  pair is refused with what is wrong.
- **Nothing assumed.** A missing number is asked for, never assumed.
- **Working shown.** Every result shows its working.

## 5. Governance: adding, reviewing, updating and retiring knowledge

Every change is one line in `kb_changes.jsonl` in the ATLAS store. The
knowledge ATLAS answers from is the repository's items with that log replayed
over them, so the log is also the audit history (`/api/knowledge/item?id=…`
shows it). The platform's audit log also records every action.

**Propose** (`knowledge.propose`, Operator or Admin):
`POST /api/knowledge/propose`. The body is one of:

```
{"item": {...}}                                      a new item
{"kind": "correction", "item": {"id": ..., changed fields}}
{"kind": "observation", "observation": "..."}        a note, attributed, never knowledge
```

A proposal is checked for:

- schema problems;
- duplicates and conflicts (same name, different definition);
- dates and editions;
- country names (it should then be a jurisdiction item);
- consequential rules;
- instruction-like text (prompt injection).

**A proposal is never answered.**

**Review** (`knowledge.review`, Admin): `POST /api/knowledge/review` with
`{"proposal_id", "decision": "approve"|"reject", "note"}`. The rules are:

- Nobody approves their own proposal.
- A proposal with schema problems cannot be approved.
- A proposal with flags or conflicts is approved only with
  `"acknowledge_flags": true` and a note saying why.
- An approved correction becomes a new version, and the old one is kept.

**Status** (`knowledge.review`): `POST /api/knowledge/status` with
`{"id", "status": "reviewed"|"approved"|"superseded"|"retired", "reason",
"superseded_by"}`. This is how a Mantrac expert approves a repository item as
the company's position, or withdraws one. Superseded and retired items stay
in the history (search with `history=1`) and are never answered as current.
A reason is required.

**Ingest an approved document** (`knowledge.review`):
`POST /api/knowledge/ingest` with `{"name", "title", "text"}` or
`{"name", "data_base64"}` for a PDF. The fields `authority` (internal,
government, standard…), `jurisdiction` and `domain` are optional. From the
command line on the server:

```
python -m intelligence.kb_govern ingest "Clearance SOP.md" --by you@mantrac.com --title "Ghana clearance SOP"
python -m intelligence.kb_govern pending
python -m intelligence.kb_govern review <proposal_id> approve --by reviewer@mantrac.com --note "checked"
python -m intelligence.kb_govern status C.gh-cif-valuation approved --by reviewer@mantrac.com
python -m intelligence.kb_govern status B.old-item retired --by reviewer@mantrac.com --reason "replaced"
```

Ingestion does the following:

- **Locations kept.** The document's sections are kept with their location
  (file › heading, line; or page for a PDF).
- **Proposals only.** Each definition line becomes a proposal, checked as
  above, with the quote and its location.
- **Scope set by source.** An internal document's rule gets scope `business`.
- **Idempotent.** Ingesting the same document twice adds nothing.

**Nothing from a document is answered until it is approved.**

**Edit the repository items** (for larger changes): edit
`knowledge/items/*.json` in git, then run `python test_knowledge.py` (schema,
links, sources) and `python tools/kb_eval.py`.

**Never.** A chat conversation never becomes knowledge. Text from documents
and items is treated as data. The engine composes answers from it, but it
never follows instructions in it.

## 6. Lessons from operation

`GET /api/knowledge/lessons` (`runs.view`) turns the verified learning store
into lessons. Each lesson has:

- its run and shipment references, carrier and workflow, and the observed
  failure;
- **every** strategy tried with its outcomes, failures included, so they are
  not repeated blindly;
- the verified resolution, ranked only after enough verdicts;
- the conditions it applies under (that carrier and that failure only).

A lesson claims no root cause: the store records outcomes, not causes.
`kb_lessons.propose_from_lesson()` turns one into an observation for a
reviewer. It becomes knowledge only as an approved item.

## 7. Assessment

`python tools/kb_eval.py --write-report` runs the 56 cases in
`knowledge/eval/eval_v1.json`. The case types are:

- definitions, and Arabic terminology;
- comparisons;
- Incoterms applied to unfamiliar situations;
- lifecycle and customs cases;
- KPI calculations and definitions;
- root-cause and recommendation questions;
- insufficient-evidence and out-of-scope questions;
- this platform's rules.

Each case is scored on retrieval, required and forbidden content, exact
values, declining, and attribution. The report is in
`knowledge/eval/REPORT.md`. **Current result: 55 of 56.** The failure is a
retrieval limit: when a question names two documents, those outrank the
"documentation discrepancy" concept. This score is optimistic: the set was
written alongside the engine and used to find its gaps. The real measure is
a held-out set written by Mantrac's logistics staff (`eval_v2.json`), run
unchanged.

## 8. Observability

Every knowledge answer is logged to `kb_queries.jsonl` in the ATLAS store.
Each entry has the question (redacted, at most 200 characters), the mode,
the top items with scores, whether anything was found, and the time taken.

`GET /api/knowledge/stats` gives:

- item counts by domain, review and evidence status;
- stale items;
- governance counts;
- load errors;
- for reviewers, the retrieval hit rate, median and 95th-percentile latency,
  and the most recent questions nothing answered (what to add next).

## 9. Implementation report

**Complete and tested**:

- **Curriculum:** the curriculum and taxonomy: 7 domains, 165 items in English
  and Arabic, 19 fully specified KPIs and 6 worked cases.
- **Validation and sources:** schema validation, and a source registry whose
  URLs were checked on 28 Oct 2026.
- **Retrieval:** search with synonyms, acronyms and Arabic, filters, and a
  two-way concept graph.
- **ATLAS answers:** layered, cited answers with status labels, from inside
  ATLAS. Run and data questions are left to the records, and every existing
  ATLAS suite still passes.
- **Calculations:** exact, never assumed, never silently repaired.
- **Governance:** proposals, four-eyes review, corrections as versions,
  supersede and retire, ingestion with location and injection flags, the
  audit log, the API, permissions and the command line.
- **Lessons:** derived from verified outcomes.
- **Assessment:** the set, the runner and the report.
- **Observability:** the query log and its statistics.

**Partly done**:

- **No review screen.** Reviewing is by API and command line; there is no
  page in the console for it yet.
- **Ingestion finds simple definitions only.** It extracts definitions written
  as "Term: …", "Term (ABC) means …" and similar. Prose rules in an SOP need a
  reviewer to propose them as items.
- **Few carrier mappings.** Carrier-specific status mappings are documented
  only where this platform's code verifies them (DHL Forwarding, DHL Express,
  DHL Aviation stations).

**Needs people or outside sources**:

- **Reviewer approval.** A Mantrac logistics expert must review and approve
  items before ATLAS presents them as Mantrac's position. Until then every
  answer says "not yet reviewed".
- **Country rules.** These must be checked against the authorities: the Ghana
  CIF valuation basis and Egypt's ACI requirement are unverified. Any other
  country rule needs its own item, with the authority and a review date.
- **Mantrac's SOPs and training material.** These should be ingested so
  Mantrac's own rules are cited as such.
- **A held-out assessment** written by Mantrac staff, to measure real
  performance.
- **Semantic retrieval** would need an embedding model. None is installed.
  If one is approved later, it can rerank `kb.search()` results; keyword
  search stays the fallback.
