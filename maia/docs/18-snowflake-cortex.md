# 18 · Snowflake Cortex: Maia's runtime intelligence

Maia's runtime LLM is **Snowflake Cortex**, and only Cortex. Claude Code is a
development tool for this repository and nothing more. There is no Claude or
OpenAI API call anywhere in the runtime. The earlier Claude proxy
(`routes_llm` on Anthropic, `claude.txt`, `agent/maia_agent.py`) has been
removed.

Status markers used below:

- **IMPLEMENTED**: code exists.
- **VERIFIED**: tested here, against fakes or the Snowflake emulator.
- **VERIFIED-LIVE**: tested against a real account.
- **TEMPORARY**: in place until something else is ready.
- **PLANNED**: not built yet.

Nothing about Cortex or Snowflake is VERIFIED-LIVE yet: no Snowflake account
was available while building it. The SIS extraction is VERIFIED-LIVE, from
the user's own runs.

## 1. Architecture

```
USER
 ↓
MAIA chat page ──(no credential, no model provider)──┐
 ↓                                                   │
FastAPI tool gateway                                 │ /v1/llm/messages (general chat)
 ├─ MaiaBrain (deterministic): intent, serial,       │ /v1/maia/answer  (equipment turn)
 │  near-matches, never substitutes a serial         │
 ├─ Snowflake Cortex ◀──────────────────────────────┘
 │    agent mode:    POST /api/v2/cortex/agent:run
 │                   with generic tools and NO tool_resources, so Cortex returns
 │                   each tool call to the gateway (client_side_execute)
 │    complete mode: SELECT AI_COMPLETE(model, prompt, …, response_format)
 │                   over the existing Snowflake SQL connection
 ├─ controlled tools (app/tools/equipment_tools.py)
 │    get_equipment_data ── EquipmentService: store → freshness → SIS → validate → persist
 │    get_equipment_parts · get_equipment_build_info · get_automation_history
 │    search_equipment · analyze_equipment · refresh_equipment_from_sis
 │                           ↓ only through EquipmentService
 │                      SIS worker (Playwright) → Caterpillar SIS
 ├─ verification: every part number, serial and date in the answer must be in
 │  this turn's tool facts, or the answer is replaced by the verified facts
 └─ Snowflake: EQUIPMENT_DATA, EQUIPMENT_PARTS, EQUIPMENT_DATA_HISTORY, AUTOMATION_RUNS
```

Isolation rules (**IMPLEMENTED, VERIFIED**):

| Rule | How it is enforced |
|---|---|
| The LLM never controls Playwright | The browser is reachable only through `EquipmentService.lookup`, called by two tools. Their arguments are a serial number and nothing else. |
| The LLM never decides a browser retry | Retries live in the SIS worker (`core/retry.py`, `RunRecorder`). `refresh_equipment_from_sis` runs the browser only if the user asked for fresh data or the stored copy is missing or stale, and at most once per turn. Otherwise it returns the stored record. |
| The LLM never receives credentials | Cortex receives tool results only: facts, provenance and run ids. SIS credentials stay in the worker (`core/secrets.py`). The Snowflake PAT or JWT lives only in the gateway's request headers, and its repr is masked. |
| The LLM never writes SQL | No tool takes SQL, a URL, a selector or a credential; a test asserts this. The only SQL is the gateway's own parameterised statements. Cortex Analyst text-to-SQL is deliberately not used. |
| The LLM never substitutes a serial | Tools accept only the serial the gateway resolved and confirmed. Anything else is refused with "ask the user". JAZ01856 → *"did you mean JAZ01865?"*, never a silent swap. |
| The LLM never fabricates data | Facts are generated by code, never by the model. `verify.py` blocks any part number, serial or date the facts don't contain. |

## 2. How Maia reaches Cortex

1. The page asks the brain (`/v1/agent/understand`). For an equipment turn it
   runs the lookup (`/v1/equipment/...`), with the live progress panel, and
   then calls **`POST /v1/maia/answer`**.
2. The gateway picks the mode (`CortexRuntime.mode()`):
   - `agent` when a PAT or key pair is configured: the Cortex Agents REST API,
     with bearer auth (`PROGRAMMATIC_ACCESS_TOKEN` or `KEYPAIR_JWT`).
   - `complete` otherwise (SSO or password): `AI_COMPLETE` with
     `response_format` over the existing driver session.
   - `MAIA_CORTEX_MODE=agent|complete` forces one.
3. The structured answer returns to the page, which renders it in place of a
   second model call. General (non-equipment) chat goes to
   **`/v1/llm/messages`**, also Cortex.

## 3. How Cortex reaches Snowflake data, and triggers SIS

Cortex never queries tables itself. In **agent mode** it asks for a tool:

```
Cortex → response.tool_use {name: "get_equipment_data", input: {serial_number}, client_side_execute: true}
gateway → run_tool() → EquipmentService.lookup → Snowflake (hit) | SIS (miss/stale) → persist
gateway → messages += tool_result {tool_use_id, content: [{type: "json", json: {facts…}}]}
Cortex → final JSON answer
```

`refresh_equipment_from_sis` works the same way. Cortex *requests* it, and the
gateway decides whether a browser actually runs.

In **complete mode** the gateway picks the tools deterministically from the
intent and from filters parsed out of the sentence ("exhaust group",
"quantity 4", "part 286-4915"). It runs them, then gives Cortex the facts in a
single `AI_COMPLETE` call.

## 4. Structured output (**IMPLEMENTED, VERIFIED**)

`POST /v1/maia/answer` returns:

```json
{ "status": "SUCCESS", "serial_number": "JAZ01865", "answer": "…",
  "facts": [{"id":"F3","statement":"JAZ01865 engine_serial_number = PRH04588","evidence":"DIRECT",
             "source":"Caterpillar SIS","retrieved_at":"…","automation_run_id":"run_…"}],
  "derived_findings": [{"statement":"…","evidence":"DERIVED","fact_ids":["F9"],"by":"gateway"}],
  "inferred": [{"statement":"…","evidence":"INFERRED","basis_fact_ids":["F3"]}],
  "missing_fields": ["operation_manual_url"], "source": "Caterpillar SIS", "origin": "store|sis",
  "retrieved_at": "…", "automation_run_id": "run_…", "confidence": "high|medium|low",
  "evidence": [{"fact_id":"F3","type":"DIRECT"}],
  "verification": {"passed": true, "blocked_tokens": []},
  "tools": [{"tool":"get_equipment_data","origin":"store","ms":12}], "sis_runs": 0,
  "cortex": {"used": true, "mode": "agent|complete", "model": "…"} }
```

- **DIRECT** is a value exactly as Snowflake or SIS returned it.
- **DERIVED** is counted, filtered or compared by gateway code.
- **INFERRED** is Cortex's own reasoning. It is always labelled, and it is
  never shown as a SIS fact.

Statuses: `SUCCESS`, `NOT_FOUND`, `LOGIN_FAILED`, `MFA_REQUIRED`,
`CAPTCHA_REQUIRED`, `WEBSITE_CHANGED`, `EXTRACTION_FAILED`,
`VALIDATION_FAILED`, `PERSISTENCE_FAILED`, `CORTEX_UNAVAILABLE`, and
`CLARIFICATION_NEEDED`, `CHAT`, `PASS`, `REFUSED`. A test fixture never
produces `SUCCESS` for the real source: `local_fixture` is a separate source,
never copied to Snowflake.

## 5. When Cortex is unavailable (**IMPLEMENTED, VERIFIED**)

The answer is `status: CORTEX_UNAVAILABLE` with `cortex.reason` and
`cortex.fix`. The verified values are still shown, labelled as the gateway's
and not as an AI answer. Nothing falls back to another model.

| reason | fix |
|---|---|
| `disabled` | `MAIA_CORTEX_ENABLED=true` (START-MAIA sets it when `snowflake.txt` exists) |
| `not_configured` | complete `snowflake.txt` / `SNOWFLAKE_*` |
| `driver_missing` | `pip install snowflake-connector-python` |
| `agent_auth` | agent mode needs a PAT or key pair; SSO and passwords use `complete` |
| `function_missing` / `privilege` | `GRANT DATABASE ROLE SNOWFLAKE.CORTEX_USER TO ROLE <role>;` |
| `model_unavailable` | another `MAIA_CORTEX_MODEL`, or `ALTER ACCOUNT SET CORTEX_ENABLED_CROSS_REGION = 'ANY_REGION';` |
| `auth_rejected`, `agent_api_missing`, `network`, `quota`, `bad_response` | as named |

## 6. Snowflake schema

| Table | Status |
|---|---|
| `EQUIPMENT_DATA`, one row per serial × source. Adds `PRODUCT` and `NORMALIZED_DATA` (migration 004). | IMPLEMENTED, VERIFIED (emulator) |
| `EQUIPMENT_PARTS`, one row per published part row: `GROUP_NAME/TITLE/PART`, `PART_NUMBER`, `PART_NAME`, `QUANTITY_REQUIRED` (+ `QUANTITY_TEXT`), `WHERE_USED`, `SERVICE_ARTICLE`, `SN_APPLICABILITY`, `COMPONENT_SERIAL`, `PART_OF`, `DESCRIPTION`, `SOURCE`, `RETRIEVED_AT`, `AUTOMATION_RUN_ID`, `RAW_DATA` | IMPLEMENTED, VERIFIED (emulator) |
| `EQUIPMENT_DATA_HISTORY` (versions), `AUTOMATION_RUNS` (audit), `AUTOMATION_RUN_CLAIMS` | IMPLEMENTED earlier |

These are the equivalents of the spec's `EQUIPMENT_DATA`, `EQUIPMENT_PARTS` and
`AUTOMATION_RUNS`. No duplicate tables were created. A column is filled only
when the page had a header for it, and every cell is kept in `RAW_DATA`.
Apply the schema with `SNOWFLAKE-SETUP.bat` (runs 001, 003, 004, and 002's
views). The Cortex grant in 004 is applied only with `--with-grants`.

## 7. SIS extraction

- **IMPLEMENTED, VERIFIED-LIVE:** the real Playwright worker, unchanged. It
  extracted JAZ01865 and C5H01697 on the user's PC: machine and engine
  serials, build dates, and the "… Entire Group (…)" sections with their
  tables from the DOM. Screenshots are audit evidence only.
- **IMPLEMENTED:** every table column the page publishes is kept (`values`
  keyed by header). Quantity, Where Used and Service Article map
  automatically *when those headers are on the page*.
- **PLANNED:** opening each group's *Individual Parts / Where Used / Service
  Articles* sub-views. That needs a selector capture on real SIS. No selector
  is guessed. Until then, those fields are `NULL` and reported as not
  published.

## 8. Environment variables (names only)

**Snowflake connection** (`snowflake.txt` holds the same keys):
`SNOWFLAKE_ACCOUNT`, `SNOWFLAKE_USER`, `SNOWFLAKE_WAREHOUSE`,
`SNOWFLAKE_DATABASE`, `SNOWFLAKE_SCHEMA`, `SNOWFLAKE_ROLE`, and one sign-in
method:

- `SNOWFLAKE_AUTHENTICATOR=externalbrowser` (SSO)
- `SNOWFLAKE_PASSWORD`
- `SNOWFLAKE_PAT`
- `SNOWFLAKE_PRIVATE_KEY_FILE` (+ `SNOWFLAKE_PRIVATE_KEY_PASSPHRASE`)

Optional: `SNOWFLAKE_HOST`. The `MAIA_SNOWFLAKE_*` equivalents take
precedence; for secrets use `…_PASSWORD_REF` / `…_PAT_REF` = `env://VAR` or
`file://path`.

**Cortex:** `SNOWFLAKE_CORTEX_ENABLED` (or `MAIA_CORTEX_ENABLED`), plus these
optional ones:

| `MAIA_CORTEX_MODEL` | `mistral-large2`, used by AI_COMPLETE |

| `MAIA_CORTEX_MAX_TOKENS` | none |
| `MAIA_CORTEX_TIMEOUT_S` | none |

**Store and SIS:**

## 9. Local development and production

- **Local:** `make test`. The Cortex tests use a fake SQL executor and a mock
  Agents endpoint. The Snowflake tests use `fakesnow`.
  `python scripts/snowflake/snowflake_setup.py cortex` makes one tiny live call.
- **Production:** a service user with key-pair auth → agent mode. Grant
  `SNOWFLAKE.CORTEX_USER` (or `CORTEX_AGENT_USER`) and set
  `MAIA_REPOSITORY=snowflake`. `GET /v1/cortex/status` shows configuration
  without secrets; `POST /v1/cortex/check` makes a live call.

## 10. Local artifacts (**TEMPORARY**, kept on purpose)

`logs/sis-results/<SERIAL>_<RUN_ID>.json|.txt` plus screenshots. They
mirror what Snowflake holds and are never the record: reads come from
Snowflake when it is the store.

## 11. Troubleshooting

- *"rules engine — Snowflake Cortex unavailable"* on replies: open
  `http://127.0.0.1:8080/v1/cortex/status`. `reason` and `fix` say what to do.
- Agent mode 401: the PAT expired, or the public key isn't set on the user
  (`ALTER USER … SET RSA_PUBLIC_KEY=…`).
- Agent mode 404: Cortex Agents isn't enabled for the account. Use
  `MAIA_CORTEX_MODE=complete`.
- `model_unavailable`: see §5.

## 12. Test procedure and results

`python -m pytest -q` in `services/automation`. `tests/test_cortex.py`
(36 tests) and the Cortex case in `tests/test_snowflake_emulator.py` prove:

- first ask: miss → SIS (fake adapter) → validate → persist to Snowflake
  (emulator), including `EQUIPMENT_PARTS` → Cortex → answer
- second ask: store hit → no browser → Cortex → answer. The logs show
  `equipment.decision action=no_cache` and then `use_cache`.
- the rest: configuration, invocation shape, structured output,
  hallucination blocking, context follow-ups, invalid serials, tool errors,
  auth failures, `WEBSITE_CHANGED` and persistence failures

**Requires a real account (not verified):** that the account, region and
role can call `AI_COMPLETE` / Cortex Agents, and that the chosen model is
available. Run `SNOWFLAKE-SETUP.bat` (it ends with the Cortex check) and paste
the output.
